# 단위 프로젝트 1차 — 요구사항 분석

> **주제**: 실시간 로그 대시보드 인터페이스
> **과목**: 웹 서비스 기초 및 AI 백엔드 개발 (192시간)
> **작성**: 2026-08-06 (개강 전 사전 분석)

---

## 과제가 요구하는 것 (원문)

1. 백엔드, DB, UI 통합 아키텍처 구현 및 **배포 실습**
2. **실시간 데이터 스트리밍**을 통한 로그 시각화 대시보드 최종 제작
3. **사용자 피드백 데이터를 반영한 AI 답변 품질 고도화** 및 서비스 최적화

---

## 요구사항을 뜯어보면

### 문장 3번이 이 과제의 정체를 알려준다

처음 읽으면 "로그를 예쁘게 보여주는 화면"으로 보이지만, 3번에 **"AI 답변 품질 고도화"**가 있다.
즉 이 프로젝트에는 **AI가 답변하는 서비스가 존재**하고, 대시보드는 그 서비스를 관측·개선하는 도구다.

정리하면 만들어야 하는 것은 두 덩어리다.

| 덩어리 | 하는 일 |
|---|---|
| **AI 서비스** | 사용자 질문을 받아 답변한다. 그 과정을 로그로 남긴다 |
| **대시보드** | 그 로그를 실시간으로 보여주고, 사용자 피드백을 모아 품질을 개선한다 |

대시보드만 만들면 3번을 충족할 수 없다. **처음부터 두 덩어리를 함께 설계**해야 한다.

### "실시간"이 뜻하는 것

새로고침을 눌러야 갱신되면 실시간이 아니다. 서버가 먼저 밀어주는 방식이 필요하다.

| 방식 | 특징 | 이 과제에 적합한가 |
|---|---|---|
| 폴링(주기적 재요청) | 구현이 쉽지만 지연·낭비가 큼 | 실시간이라 보기 어려움 |
| **SSE** (Server-Sent Events) | 서버 → 클라이언트 단방향 밀어주기 | ✅ 로그 흐름에 가장 맞음 |
| WebSocket | 양방향 | 채팅에는 좋지만 로그 표시엔 과함 |

로그는 **서버에서 클라이언트로만** 흐르므로 SSE가 자연스럽다.
단, AI 답변을 한 글자씩 흘려보내는(스트리밍) 화면까지 만들면 그때도 SSE를 재사용할 수 있다.

### "배포 실습"을 얕보면 안 된다

최종 프로젝트의 **성과지표가 "웹 서비스 배포"**다. 1차에서 배포를 제대로 해두면 그 뒤가 편해진다.
내 컴퓨터에서만 도는 것은 배포가 아니다. **남이 주소로 접속할 수 있어야** 한다.

## 만들어야 할 구조 (초안)

```
[사용자] ──질문──▶ [FastAPI 백엔드] ──▶ [AI 모델 API]
    ▲                    │
    │                    ├──▶ [DB] 질문·답변·응답시간·피드백 저장
    │                    │
    └──피드백(👍/👎)──────┘
                         │
                    [SSE 스트림]
                         │
                         ▼
                 [대시보드 화면]
          실시간 로그 · 응답시간 그래프 · 피드백 통계
```

### 화면에 무엇을 보여줄 것인가

로그를 그냥 나열하면 "보기만 하는 화면"이 된다. **판단에 쓰이는 화면**이어야 한다.

- 실시간 로그 흐름 (레벨별 색 구분: INFO / WARN / ERROR)
- 응답 시간 추이 — 느려지는 구간이 보이는가
- 오류율 — 갑자기 오르면 눈에 띄는가
- **피드백 통계** — 👎를 받은 답변이 무엇이었는지 바로 볼 수 있는가

마지막 항목이 요구사항 3번과 직접 연결된다.

### DB에 무엇을 남길 것인가

```
logs            시각 · 레벨 · 메시지 · 처리시간
conversations   질문 · 답변 · 사용한 모델 · 토큰 수 · 응답시간
feedback        어떤 답변에 · 좋아요/싫어요 · 남긴 이유
```

`feedback` 테이블이 없으면 3번을 할 수 없다. **설계 단계에서 빠뜨리기 쉬우니 처음부터 넣는다.**

---

## 요구사항 3번을 어떻게 충족할 것인가

"AI 답변 품질 고도화"는 모호하게 들리지만, 실제로는 **측정 → 원인 파악 → 개선 → 재측정** 순환이다.

1. **측정**: 피드백(👍/👎)과 응답시간을 쌓는다
2. **원인 파악**: 👎를 받은 질문들의 공통점을 본다 (특정 주제? 긴 질문? 특정 시간대?)
3. **개선**: 프롬프트를 고치거나, 자주 나오는 질문은 미리 준비된 답을 쓰거나, 모델을 바꾼다
4. **재측정**: 개선 전후의 👎 비율을 비교한다

**개선했다고 주장하는 것과 개선을 보여주는 것은 다르다.**
발표할 때 "이렇게 바꿨더니 부정 피드백이 몇 % 줄었다"고 숫자로 말할 수 있어야 한다.
그러려면 **개선 전 데이터가 남아 있어야** 하므로, 피드백 수집을 최대한 일찍 붙여야 한다.

## 미리 정리해 둔 위험 요소

| 위험 | 왜 문제인가 | 대비 |
|---|---|---|
| **API 키 유출** | 되돌릴 수 없음 | `.env` + 커밋 차단 장치 (적용 완료) |
| **API 비용 폭주** | 무한 루프 한 번에 요금 발생 | 호출 횟수 제한, 사용량 로그를 대시보드에 표시 |
| **DB에 개인정보 저장** | 사용자 질문에 개인정보가 섞일 수 있음 | 저장 전 마스킹 검토, DB 파일은 커밋 제외 |
| **배포를 마지막에 시도** | 배포는 항상 예상보다 오래 걸림 | **빈 화면이라도 먼저 배포**하고 기능을 채워 넣는다 |
| **피드백 기능을 나중에 추가** | 개선 전 데이터가 없어 효과 증명 불가 | 초기 구현에 포함 |

마지막 두 개가 특히 중요하다. 둘 다 **"나중에 하면 된다"고 미루기 쉬운데, 미루면 과제 요구사항을 충족하지 못하게 되는** 항목이다.

## 수업 진도와 맞춰 보기

| 수업 | 시간 | 이 프로젝트에서 쓰이는 곳 |
|---|---|---|
| 파이썬 백엔드 개발 및 Vibe Coding | 80h | FastAPI 서버, API 설계 |
| DB 연동 및 세션 관리 | 40h | 로그·대화·피드백 테이블 설계 |
| AI 인터페이스 및 UX 설계 | 48h | 대시보드 화면, 피드백 UI |
| 단위 프로젝트 (1차) | 24h | 통합 · 배포 · 발표 |

**단위 프로젝트에 배정된 시간은 24시간(3일)뿐이다.**
그 3일에 처음부터 만들려 하면 못 끝낸다. 수업에서 배운 것을 **그때그때 이 프로젝트에 붙여 나가는 것**이 현실적이다.

### 그래서 이렇게 하기로 한다

- **파이썬 백엔드 수업 중**: 질문을 받아 답하는 최소 API를 만들고, **빈 껍데기 상태로 먼저 배포해 본다**
- **DB 수업 중**: 세 개의 테이블을 붙이고 로그를 쌓기 시작한다 (피드백 테이블 포함)
- **UX 수업 중**: 대시보드 화면과 피드백 버튼을 만든다
- **단위 프로젝트 3일**: 통합 · 개선 실험 · 결과 정리 · 발표 준비
